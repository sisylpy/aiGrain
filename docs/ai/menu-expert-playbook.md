# Menu Expert Playbook：餐饮菜单专家方法论

## 1. 文档定位

本文档用于指导「菜单经营顾问 / MenuOperation Agent」的长期设计。

目标不是让大模型自由发挥，直接替老板做经营判断，而是建立一套稳定、可解释、可复盘的菜单经营分析方法论。

系统分工必须保持：

* LLM：负责理解用户问题、选择语义合同、把结构化结论表达得更像顾问。
* Tool：负责查询真实经营数据。
* AnswerPlan Builder：负责确定性业务判断、分组、排序、建议动作生成。
* Renderer / Composer：只读 AnswerPlan 表达，不重新计算、不重新判断。
* 前端：只渲染 cards[]，不计算业务结论。

菜单专家的核心能力应该是：

> 基于真实经营数据，把菜品划分角色，识别利润风险，给出有证据、有优先级、可执行的菜单优化建议。

---

## 2. 菜单专家的核心问题

菜单专家主要回答以下几类老板问题：

### 2.1 菜单整体经营

示例问法：

* 这个月菜单经营怎么样？
* 我这个菜单结构合理吗？
* 哪些菜是明星菜、引流菜、潜力菜、淘汰菜？

目标能力：

* 分析菜单整体结构。
* 将菜品按销量和利润划分角色。
* 给老板一个菜单结构概览。

---

### 2.2 畅销低利风险

示例问法：

* 哪些菜卖得多但利润低？
* 哪些畅销菜毛利偏低？
* 哪些菜拖累整体毛利？

目标能力：

* 找出销量较高但利润效率偏低的菜。
* 区分“毛利偏低”和“实际亏损”。
* 给出降本、复核成本、调整售价等建议。

---

### 2.3 菜单优化方案

示例问法：

* 菜单怎么优化？
* 这个月有哪些菜需要调整？
* 哪些菜应该主推、降本、观察或下架？

目标能力：

* 不是简单列 action list。
* 应输出有优先级、有证据、有执行步骤的菜单优化方案。
* 让老板知道先处理什么、为什么处理、怎么处理。

---

### 2.4 单菜利润处方

示例问法：

* 香煎青鱼价格和配方怎么优化？
* 香煎青鱼价格合适吗？
* 香煎青鱼为什么毛利不高？
* 香煎青鱼按 55% 目标毛利率应该卖多少钱？

目标能力：

* 综合售价、实际成本、理论成本、配料、毛利、目标毛利和行动建议。
* 输出单菜经营处方。
* 不是简单建议售价计算器。

---

## 3. 菜单四象限方法

菜单结构分析采用「销量 × 实际利润」的相对分层方法。

P1 阶段使用本轮菜品集合内的中位数作为动态阈值：

* 销量 >= 本轮销量中位数：高销量
* 销量 < 本轮销量中位数：低销量
* 实际利润 >= 本轮实际利润中位数，且实际利润非负：高利润
* 实际利润 < 本轮实际利润中位数，或实际利润为负：低利润

### 3.1 明星菜 STAR

特征：

* 高销量
* 高利润

经营含义：

* 既能带来客流，又能贡献利润。
* 是菜单中最值得保护和稳定供应的菜。

建议动作：

* 保留并主推。
* 稳定出品质量。
* 保证供应。
* 可放在菜单推荐位或首页显眼位置。

禁止表达：

* 不要因为成本高就直接建议下架。
* 不要没有证据就建议降价促销。

---

### 3.2 引流菜 TRAFFIC

特征：

* 高销量
* 低利润

经营含义：

* 能带来销量和顾客关注，但利润效率偏低。
* 不能简单认为是坏菜，也不能直接下架。

建议动作：

* 优先复核成本结构。
* 检查主料出库、损耗、标准用量。
* 必要时小幅调价。
* 可搭配高毛利菜做套餐。

禁止表达：

* 不要直接说“亏钱”，除非实际利润为负。
* 不要直接建议下架畅销菜。
* 不要把毛利偏低等同于经营失败。

---

### 3.3 潜力菜 POTENTIAL

特征：

* 低销量
* 高利润

经营含义：

* 利润空间好，但曝光或点单不足。
* 可能是值得推广的利润菜。

建议动作：

* 增加推荐位。
* 优化菜名、图片和描述。
* 和畅销菜做套餐搭配。
* 让服务员重点推荐。

禁止表达：

* 不要直接判断“顾客不喜欢”。
* 不要在没有销量周期对比时判断为失败菜。

---

### 3.4 淘汰菜 ELIMINATE

特征：

* 低销量
* 低利润

经营含义：

* 对销量和利润贡献都弱。
* 是优先观察、调整或下架的候选。

建议动作：

* 先观察连续周期表现。
* 复核是否有定价、出品、曝光问题。
* 可考虑改配方、改菜名、减少备货。
* 连续低效后再考虑下架。

禁止表达：

* 不要单周期直接建议下架。
* 不要没有库存、备货、顾客反馈证据就武断淘汰。

---

## 4. 建议动作枚举

建议动作必须由 AnswerPlan Builder 根据数据生成，不能由 LLM 自由判断。

### 4.1 KEEP_AND_PROMOTE：保留并主推

适用场景：

* 明星菜。
* 销量和实际利润都表现较好。
* 对菜单贡献明确。

允许表达：

* 建议继续保留。
* 建议保持推荐位。
* 建议稳定供应。

禁止表达：

* 不要建议降价，除非另有促销目标。
* 不要建议随意改配方。

---

### 4.2 COST_REVIEW：复核成本

适用场景：

* 高销量但毛利率偏低。
* 实际成本高于理论成本。
* 主料成本占比较高。
* 实际利润偏低但不一定亏损。

允许表达：

* 建议复核主料用量。
* 建议检查出库成本。
* 建议检查损耗、废弃、报损。
* 建议复核标准配方执行。

禁止表达：

* 不要直接说最新采购价上涨，除非系统已接入最新采购价。
* 不要直接给出具体克数调整，除非系统有明确标准和安全依据。

---

### 4.3 PRICE_REVIEW：复核价格

适用场景：

* 当前售价低于目标毛利建议售价。
* 实际成本较高，成本短期难以下降。
* 目标毛利率明确。

允许表达：

* 建议评估小幅调价。
* 建议结合顾客接受度和销量观察。
* 建议优先降本，成本无法下降时再调价。

禁止表达：

* 不要直接说必须涨价。
* 不要忽略销量和顾客接受度。
* 不要让前端或 Composer 计算建议售价。

---

### 4.4 RECIPE_REVIEW：复核配方

适用场景：

* 理论成本与实际成本偏差明显。
* 主料用量可能偏高。
* 配料成本集中度较高。

允许表达：

* 建议复核标准用量。
* 建议复核后厨执行。
* 建议检查主料称重和出品规格。

禁止表达：

* P1 不直接建议“把某配料从 300g 改成 250g”。
* 不要在没有配方标准依据时修改出品方案。

---

### 4.5 INCREASE_EXPOSURE：增加曝光

适用场景：

* 高毛利但低销量。
* 潜力菜。
* 利润效率不错但点单不足。

允许表达：

* 建议放到推荐位。
* 建议优化菜名、图片、描述。
* 建议与畅销菜做套餐。

禁止表达：

* 不要说一定会提升销量。
* 不要在没有顾客反馈时断言菜品不受欢迎。

---

### 4.6 WATCH：观察调整

适用场景：

* 数据样本少。
* 单周期表现异常。
* 低销量低利润但证据不足以下架。

允许表达：

* 建议继续观察一个周期。
* 建议减少备货风险。
* 建议复核曝光、定价和出品。

禁止表达：

* 不要直接下架。
* 不要把短期波动当长期趋势。

---

### 4.7 CONSIDER_REMOVAL：考虑下架

适用场景：

* 连续多个周期低销量、低利润。
* 已复核曝光、价格、配方后仍表现低效。
* 对库存、备货或后厨效率造成明显负担。

P1 限制：

* P1 默认不主动给“下架”强建议。
* P1 最多表达为“观察后考虑调整/下架”。

禁止表达：

* 不要单周期直接建议下架。
* 不要没有连续周期证据就强结论。

---

## 5. 菜单优化方案卡设计原则

`MENU_ACTION_RECOMMENDATION_CARD` 不应该只是 action list。

它应该升级为「菜单优化方案卡」，回答：

* 当前菜单最大优化点是什么？
* 先处理哪些菜？
* 哪些菜要保护？
* 哪些菜要降本？
* 哪些菜要增加曝光？
* 哪些菜观察调整？
* 老板本周应该做哪几件事？

建议 payload 包含：

```json
{
  "optimizationSummary": "本月菜单优化重点是先处理畅销低利菜，同时稳定利润贡献菜。",
  "priorityGroups": [],
  "protectDishes": [],
  "costReviewDishes": [],
  "promotionDishes": [],
  "watchListDishes": [],
  "nextSteps": [],
  "evidenceRows": [],
  "capabilityLimits": []
}
```

### 5.1 optimizationSummary

必须是一句话经营结论。

示例：

* 本月菜单优化重点不是增加新品，而是先复核畅销低利菜的成本，同时稳定明星菜供应。
* 当前菜单中引流菜占比较高，建议先做成本复核和套餐搭配，不建议直接下架畅销菜。

---

### 5.2 priorityGroups

按优先级组织建议。

建议分组：

1. 优先处理：畅销低利、实际利润偏低、毛利拖累菜。
2. 稳定主推：高销量、高利润、贡献稳定的菜。
3. 增加曝光：高毛利、低销量的潜力菜。
4. 观察调整：低销量、低利润或样本不足的菜。

每组必须包含：

* groupName
* priority
* reason
* dishes
* suggestedAction

---

### 5.3 nextSteps

给老板 3 条以内可执行动作。

示例：

1. 先复核酸奶碗的主料出库、标准用量和损耗。
2. 对核桃芽菜西芹先查成本结构，再决定是否调价。
3. 香煎青鱼和椒麻鸡保持推荐位和供应稳定。

nextSteps 必须来自 AnswerPlan 结构化结果，不能由 LLM 自由编造。

---

## 6. 单菜利润处方卡设计原则

`DISH_PROFIT_PRESCRIPTION_CARD` 是单菜深度诊断能力。

它不是简单定价计算器。

它必须综合：

* 当前售价
* 实际成本
* 理论成本
* 目标毛利率
* 建议售价
* 理论成本与实际成本差异
* 配料明细
* 主要成本来源
* 用量、出库、损耗复核建议
* 综合行动建议

P1 允许表达：

* 当前价格是否大致合理。
* 按目标毛利率计算的建议售价。
* 实际成本是否高于理论成本。
* 哪些配料或主料值得复核。
* 是否优先建议降本、复核用量、观察调价。

P1 禁止表达：

* 最新采购价上涨。
* 外部市场售价对比。
* 网上同类菜做法。
* 跨门店单菜排名。
* 直接修改具体配方克数。
* 替代配料推荐。

---

## 7. LLM 使用边界

LLM 可以做：

* 理解用户问题。
* 选择语义合同。
* 根据 AnswerPlan 做自然语言表达。
* 把结构化建议说得像老板顾问。

LLM 不可以做：

* 自己判断某菜应该下架。
* 自己判断某菜应该涨价。
* 自己判断某菜亏损。
* 自己编造配料、成本、价格。
* 自己引用最新采购价或外部市场价。
* 自己重排菜品优先级。
* 自己生成无证据的经营结论。

如果 AnswerPlan 没有证据，LLM 必须表达：

> 当前数据不足以支持该判断。

---

## 8. Java / AnswerPlan 责任边界

Java AnswerPlan Builder 负责：

* 菜品四象限分类。
* 动作类型生成。
* 优先级生成。
* 菜品分组。
* 建议售价公式计算。
* 理论成本与实际成本差异判断。
* evidenceRefId 绑定。
* knownGaps / capabilityLimits 生成。

Java 不应该做：

* 用 contains / alias / remap 猜用户意图。
* 在合同外强行切换 planType。
* 编造 Tool 没有的数据。
* 把 P2/P3 能力塞进 P1 文案。

---

## 9. Renderer / Composer 责任边界

Renderer / Composer 只能：

* 读取 AnswerPlan。
* 读取 cards[] payload。
* 用自然语言表达已有事实和建议。

Renderer / Composer 不能：

* 重新计算毛利率。
* 重新排序菜品。
* 重新判断建议动作。
* 从 toolResults 直接拼事实。
* 把 knownGap 英文 code 暴露给老板。

---

## 10. 前端责任边界

前端只负责展示 cards[]。

前端不能：

* 计算建议售价。
* 判断菜品分类。
* 判断是否下架、涨价、主推。
* 从 answerPreview 中解析业务字段。

前端应该：

* 根据 cardType 选择组件。
* 读取 payload 渲染。
* 对 capabilityLimits 做中文提示。
* 不展示英文 knownGap code。

---

## 11. P1 / P2 / P3 边界

### P1：内部经营数据

支持：

* 菜单四象限
* 畅销低利菜
* 菜单优化行动建议
* 单菜利润处方
* 建议售价
* 理论成本 vs 实际成本
* 配料复核建议

不支持：

* 最新采购价
* 外部市场价
* 网上同类菜售价
* 跨门店单菜排名
* 自动修改配方克数
* 替代配料推荐

---

### P2：内部经营增强

可增加：

* 最新采购 / 入库价
* 采购价趋势
* 跨门店同菜对比
* 成本趋势
* 菜品四象限角色写入单菜处方卡
* 配料成本 Top3 变化

---

### P3：外部市场参考

可增加：

* 外部平台价格参考
* 同类菜做法摘要
* 同城 / 同档次参考
* 外部 benchmark 置信度

要求：

* 必须标注来源、时间、置信度。
* 只能作为辅助参考。
* 不能覆盖本店真实经营数据。

---

## 12. 总原则

菜单专家不是“自由发挥的 AI”。

菜单专家应该是：

> 真实经营数据 + 确定性 AnswerPlan + 餐饮菜单方法论 + LLM 顾问式表达。

系统必须保证：

* 事实可追溯。
* 建议有证据。
* 结论可复盘。
* 能力边界清楚。
* 不把 P2/P3 伪装成 P1。
* 不让大模型替代业务判断。
